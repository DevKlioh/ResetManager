Introduction

ResetManager is a Minecraft server administration plugin for controlled item and build resets within a defined world boundary. It combines persistent placement tracking, optional historical CoreProtect lookups and experimental reference terrain comparison to identify eligible blocks and containers.

Use ITEMS to clear inventories and equipment, or BUILDS to remove recorded builds and attempt to restore differences against compatible generated terrain. Both operations require confirmation. It is intended for maintenance and seasonal resets, not as a replacement for backups or a general-purpose rollback plugin.

Why ResetManager?

ResetManager brings several reset workflows together in one plugin. Rather than deleting a world folder or relying solely on manual region selection, administrators can select a world and reset type.

Approach ResetManager's distinction
Full world deletion Works within an existing world and scan boundary.
Manual block cleanup Uses placement records and optional reference comparison.
History-only cleanup Can attempt to identify older untracked material differences.
Inventory-only tools Combines world item cleanup with global vanilla player inventory cleanup.
Fixed-speed processing Offers four reference-change budgets and adaptive throttling.

Installation

  1. Back up all worlds, vanilla playerdata and existing plugin data. Test on a disposable copy.
  2. Obtain the release JAR ResetManager-v0.0.1.jar from the publisher. Place it in plugins/.
  3. Start the server and inspect the startup banner and logs.
  4. Stop the server or edit configuration during maintenance; review plugins/ResetManager/config.yml and messages.yml.
  5. Restart for database changes; /rm reload reloads YAML settings.
  6. Run /rm help and verify permissions. Before BUILDS, confirm the world generation is compatible or disable comparison.

Existing YAML files may not automatically receive new defaults. Compare them with the bundled examples. Do not overwrite your database or recovery lock file.

Core features

  • Separate ITEMS and BUILDS operations.
  • Native world border support and configurable fallback diameter.
  • Generated chunk discovery, including compatible pregenerated chunks; target chunks are not intentionally generated by the reset.
  • Persistent placement and interaction tracking using SQLite or MySQL.
  • Optional historical CoreProtect lookup for placements and containers.
  • Experimental seed-based reference terrain comparison, asynchronous snapshot comparison and section fingerprints.
  • Persistent verification cache and tracked-chunk prioritization.
  • ECO, BALANCED, TURBO and CUSTOM reference block-change budgets.
  • Adaptive TPS/MSPT throttling for BUILDS.
  • Mandatory target-world lockdown for BUILDS, configurable server admission policy and persistent recovery locks.
  • Sender-specific confirmation, one active reset, console progress and failure reporting.

Reset types

ITEMS

Clears eligible block container contents (including older containers), lecterns, decorated pots, chiseled bookshelves, dropped items, item-frame contents, armor stand equipment, inventory-holder entities and mob equipment inside the selected boundary. Identifiable untouched natural loot-table containers are preserved. Older natural containers without loot-table metadata may be cleared.

Global impact: all online and offline vanilla player inventories, armor, offhand and Ender Chests are cleared across every world. New logins are blocked during ITEMS. Offline processing assumes the primary world's playerdata directory; third-party inventory stores are not covered. Other root NBT data is retained by the offline wiper.

BUILDS

Removes tracked placements, available historical placements and detected touched containers. Reference comparison generates a temporary compatible world and compares material differences at matching coordinates, restoring reference block data for eligible differences. Tracked/history removals are applied separately as air, so exact terrain restoration is not guaranteed. State-only differences are not restored by comparison.

The target world must be empty. Untouched natural containers are intended to remain when they match the reference; mismatched generation or missing history can defeat classification. Neither player age nor ownership is an intentional exemption. No complete detection guarantee exists.

Boundary

A custom vanilla world border defines the scan square. Otherwise the default fallback is 15,000 blocks in diameter (7,500 from center to edge), centered at X=0, Z=0. The actual world border is not changed.

Commands

Command Purpose
/rm or /rm help Show command guide
/rm version Show version and author
/rm reload Reload configuration and messages; database changes require restart
/rm world <world> items Request an ITEMS reset
/rm world <world> builds Request a BUILDS reset
/rm confirm Confirm your pending request
/rm cancel Cancel your pending request, not a running job

All commands require resetmanager.admin. The target world must be loaded. Confirmation expires after 60 seconds by default and must come from the same sender. The world and boundary are checked again at confirmation. Only one reset may run at once.

Console example

With default BUILDS lockdown, disconnect everyone first. Enter in the server console (without slash):

rm world world builds
rm confirm

Read the confirmation warning before proceeding. Replace world with the actual world name. Do not use ITEMS unless a global player inventory wipe is intended.

Permissions

Node Default Access
resetmanager.admin OP All ResetManager commands

No separate reset-type or lockdown bypass permission is declared. The except admission policy checks operator status, not this permission. Operators cannot bypass target-world lockdown. Grant administrative access only to trusted staff.

Configuration examples

The following YAML examples are preserved from the supplied documentation package.

config.yml

# A vanilla-default-size world border triggers this fallback scan boundary.
fallback-border-diameter: 15000
fallback-center-x: 0
fallback-center-z: 0
# Chunks processed per server tick; adjust conservatively.
chunks-per-tick: 1
confirmation-seconds: 60
progress-interval-seconds: 3
# Maximum candidate chunks in a single reset (0 = unlimited).
max-candidate-chunks: 0

# Item resets scan existing containers, even when they predate installation.
# Identifiable unopened natural loot-table containers are preserved.
# IMPORTANT: old natural containers without loot-table metadata cannot be reliably distinguished.

# Tracking storage. Changing database.type requires a server restart.
# Existing SQLite data is not automatically copied to MySQL (or vice versa).
database:
  type: sqlite # sqlite or mysql
  mysql:
    host: localhost
    port: 3306
    database: resetmanager
    username: root
    password: ""

# Offline player .dat files processed per server tick during the final ITEMS phase.
offline-player-files-per-tick: 5

builds-reset:
  coreprotect-history: true
  legacy-comparison:
    enabled: true
    # WARNING: true assumes matching vanilla generation; disable for incompatible worlds.
    confirm-compatible-generation: true
    persistent-cache: true
    # Change when datapacks or generation settings change.
    cache-generation-id: default
  performance:
    # ECO = 128, BALANCED = 512, TURBO = 2048 reference block changes per tick.
    # CUSTOM uses blocks-per-tick below; preset modes ignore that setting.
    # WARNING: CUSTOM values above TURBO (2048) may cause severe tick lag,
    # TPS drops, freezes or watchdog shutdowns. Test on a backup first.
    # Adaptive throttling cannot guarantee protection against a long tick.
    mode: ECO
    # CUSTOM only: positive integer (1 to 2147483647); invalid values use 128.
    blocks-per-tick: 128
    adaptive-throttling: true
    minimum-tps: 19.0
    maximum-mspt: 45.0

# Target-world lockdown is mandatory for BUILDS, regardless of server entry policy.
world-lockdown:
  # true (recommended): nobody may join; console only, empty server required.
  # false: players may join other worlds.
  # except: operators only; non-operators must disconnect before starting.
  # Operators never bypass target-world lockdown.
  block-server-entering: true
  fallback-world: "spawn"
  redirect-on-login: true
  redirect-on-respawn: true

messages.yml

# Messages use light aqua, white, soft gray, green, and warning amber.
no-permission: 'You do not have permission to use ResetManager.'

comparison-world-occupied: '&eReset blocked: &f{world} contains {players} player(s). Evacuate everyone and request the reset again.'
comparison-entry-blocked: '&eThis world is temporarily unavailable during a BUILDS reset.'

server-empty-required: '&eDisconnect all players, including operators, and run the reset from console.'
operators-only-required: '&eAll non-operators must disconnect before this reset.'
server-entry-blocked: '&eA world reset is running. Please reconnect after it completes.'
world-redirected: '&eYou have been redirected while the world reset is running.'
world-unlocked: '&aWorld reset complete; entry restored.'

Performance modes

Mode Reference block changes per tick
ECO (default) 128
BALANCED 512
TURBO 2048
CUSTOM Positive integer configured by owner 
builds-reset:
  performance:
    mode: ECO
    blocks-per-tick: 128
    adaptive-throttling: true
    minimum-tps: 19.0
    maximum-mspt: 45.0

Preset modes ignore blocks-per-tick. CUSTOM accepts 1–2147483647; invalid values fall back to 128. Values above 2048 risk severe lag, freezes or watchdog shutdowns. Adaptive throttling pauses BUILDS work when TPS is below the threshold or average MSPT exceeds its threshold; it cannot prevent every long tick.

The budget applies only to reference changes, not all tracked removals, chunk loads or history queries. First scans can take considerable time. Section hashing still reads block data; cache hits avoid reference chunk regeneration, not all scanning. No performance guarantee or benchmark is implied.

World lockdown

Target-world lockdown is mandatory for BUILDS, even when comparison is disabled.

world-lockdown:
  block-server-entering: true
  fallback-world: "spawn"
  redirect-on-login: true
  redirect-on-respawn: true
Policy Behavior during BUILDS
true (recommended) Empty server required; console only; everyone denied including OPs
false Players may join other worlds; target must remain empty
except Only OPs may join; non-OPs must disconnect before start

Teleport and portal entry are blocked; login, respawn and world-change safeguards redirect or kick when needed. If the preferred fallback is unavailable, another unrestricted loaded world may be used. Unexpected occupancy is checked before BUILDS work; unresolved entry aborts the job.

world-locks.yml persists target-world locks across interruptions. Successful BUILDS completion releases the lock; failures retain it. Server-wide admission restrictions apply during the active job, not indefinitely after a restart. To recover, investigate errors, back up and rerun the same BUILDS request from console. There is no dedicated unlock or exact resume command. Do not casually delete the lock file.

Database and cache

SQLite is the default (plugins/ResetManager/resetmanager.db). MySQL is optional using database.type: mysql and the host, port, database, username and password settings. Drivers are bundled. Restart to reconnect; changing backends does not migrate records automatically.

Legacy tracking.yml is imported only when the selected database is empty, then archived after successful persistence. Tracking records are loaded into memory and periodically saved; large datasets may increase memory and persistence costs.

The verified_chunks table stores fingerprints for chunks with no material differences at comparison time. Cache keys include world and generation signature. Change cache-generation-id when generation settings or datapacks change. Matching live fingerprints can skip reference regeneration, but history and tracking checks still run. Modified chunks are rechecked. Rerunning after interruption may reuse cache; exact checkpoint or automatic continuation is not implemented.

Back up database and world data together. Protect MySQL credentials and do not publish your live config.

Soft dependencies

Plugin Required? Role
CoreProtect No Optional historical placement and container lookup through its API. Requires compatible API and retained logs.
Chunky No Pregenerated chunks can be scanned; declared as a soft dependency for load ordering. No direct Chunky API integration.

Both are detected in the startup banner when enabled. Without CoreProtect, internal tracking and enabled reference comparison remain available. Historical lookup failures can result in failed chunks. CoreProtect history is not a complete provenance record.

Frequently asked questions

Does ResetManager delete the world?

No. It modifies eligible blocks, items and player data within the described scopes.

Can it detect builds before installation?

It attempts this through retained CoreProtect history and compatible reference comparison. Neither guarantees complete detection.

Does it remove offline players' builds?

Recorded or identifiable builds are processed regardless of owner online status.

Will ITEMS clear my inventory in another world?

Yes. Vanilla player inventories and Ender Chests are globally cleared, including offline records in the supported directory.

Are natural chests safe?

Identifiable untouched loot-table containers are preserved by ITEMS. BUILDS removes detected touched containers. Missing metadata or generation differences can lead to incorrect classification.

Do I need CoreProtect or Chunky?

No. They are optional; CoreProtect improves historical evidence when compatible logs exist.

Can I reset while players are online?

Default BUILDS policy requires everyone offline and console execution. Other policies permit access to other worlds, never the target. ITEMS blocks new logins.

Can I cancel a running reset?

/rm cancel only cancels a pending request. There is no documented active-job cancellation command.

Will the first comparison be fast?

Not necessarily. Large pregenerated worlds may take a long time; subsequent cache hits can reduce work.

Does it support custom terrain?

Reference comparison rejects a non-null custom generator and cannot guarantee compatibility with datapacks or upgraded worlds. Disable comparison for incompatible generation.

Can I undo a reset?

No built-in undo. Restore verified backups.

Does it support every Paper fork?

No universal compatibility claim is made. Test your exact server build.

Troubleshooting

Symptom Action
Reset blocked: players present Evacuate target; with default policy disconnect everyone and use console.
No valid confirmation Repeat request and confirm as same sender before timeout.
World not found Check exact name and ensure world is loaded.
Reference initialization failed Check console, generator compatibility, height and available disk space; disable comparison for incompatible worlds.
Progress appears stalled Check TPS/MSPT, reference generation and database/history queries; adaptive throttling may pause work.
Chunk failures Inspect stack traces and CoreProtect API compatibility; do not treat a failed job as complete.
World remains locked after restart Recovery lock is intentional; investigate, back up and rerun BUILDS.
Old configuration defaults remain Merge new keys from bundled examples; restart for database changes.
Offline player failures Check file access, primary playerdata path and logs; restore backups if needed.

When reporting an issue include plugin version, exact server build, Java version, relevant configuration with secrets removed, reset type and console log.

Safety and limitations

Resets are destructive and not transactionally atomic. Always keep verified backups of worlds, playerdata and tracking storage. Test on a disposable copy and schedule maintenance.

Reference comparison is enabled by default in this release but remains experimental. Matching seed, environment, world type, structure settings and height do not prove identical generation. Version changes, datapacks, natural growth, fluids and explosions can create differences unrelated to players. Identical replacements cannot be detected from terrain alone. State-only differences are not restored. Tracking and history are incomplete for indirect edits and some plugin changes.

For incompatible worlds disable builds-reset.legacy-comparison.enabled; internal tracking and available history remain useful. Do not set compatibility approval to true merely to bypass an error. A full reset may take hours or longer; no guaranteed runtime or lag-free operation exists.

Check completion logs for zero chunk/player failures and inspect results before reopening. Interrupted BUILDS can retain a persistent world lock. Cache reuse is not a transactional recovery mechanism. No built-in undo exists. Third-party player inventory stores and nonstandard region layouts are not guaranteed to be covered.
